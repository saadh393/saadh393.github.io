## The Problem

Most tutorials show you how to upload a video. None of them show you what breaks when 500 people try to watch it at the same time — and your backend is a single Node.js process doing synchronous FFmpeg calls.

I wanted to understand the failure modes before I hit them in production. So I built a system to stress-test them deliberately.

## Key Design Decisions

### Why BullMQ over a direct FFmpeg call?

FFmpeg is synchronous and CPU-bound. If you call it inline in an Express handler, every upload blocks the event loop — request #2 waits for request #1's transcode to finish. With BullMQ:

- Uploads return immediately with a job ID
- Workers process concurrently up to `concurrency` limit
- Failed jobs are automatically retried with backoff

<Callout type="tradeoff">
  FFmpeg is intentionally single-threaded per job. Horizontal scaling (more worker containers) is cheaper than vertical scaling (more CPU per worker), and simpler to reason about.
</Callout>

### Why MinIO over S3?

Local dev. MinIO has an S3-compatible API — swapping to S3 in production is a one-line config change.

### Segment duration: 2 seconds

HLS segment duration is a trade-off between latency and buffering. 2s segments give low latency at the cost of more HTTP requests. For a video platform serving on-demand content (not live streams), this is the right call.

<Callout type="insight">
  Shorter segments = lower start latency but more manifest overhead. For live streaming, 1s is common. For VOD, 4-6s is fine. We optimized for perceived startup time.
</Callout>

## What I Learned

<Timeline>
  <Event date="Week 1" label="Designed service boundaries" note="Drew the architecture before writing a line of code. Changed it twice." />
  <Event date="Week 2" label="FFmpeg + BullMQ working end-to-end" note="First successful transcode at 3am. Segment duration was 10s by mistake." />
  <Event date="Week 3" label="MinIO integration + Docker Compose" note="Hardest part: getting MinIO presigned URLs to work inside the Docker network." />
  <Event date="Week 4" label="Load test: 500 concurrent simulated viewers" note="Zero queue overflow. Bottleneck was MinIO read IOPS, not the worker." />
</Timeline>

<Callout type="result">
  The bottleneck under load was not FFmpeg, not BullMQ, and not the Node.js upload service. It was MinIO IOPS on the local Docker volume. In production, swap MinIO for S3 and this ceiling disappears.
</Callout>

## Stack

- **Node.js + Express** — Upload service and HLS server
- **BullMQ** — Distributed job queue
- **Redis** — BullMQ backing store
- **FFmpeg** — Video transcoding (spawned as child process)
- **MinIO** — S3-compatible object storage
- **Docker Compose** — Orchestration layer

The full source is on [GitHub](https://github.com/saadh393/distributed-hls-streaming-platform).
